# Claude-Codex 병렬 개발 워크플로

Claude Fable은 계획과 재계획만 맡고, Codex Sol/Terra는 구현과 검증을 맡는다. 기본값은 **토큰 우선 균형형**이다. 안전에 필요한 검증은 유지하되 같은 문맥과 검증을 여러 모델에 반복 입력하지 않는다.

## 기본 실행 프로필

- Fable 최초 계획 1회, 동일 차단 원인에 대한 재계획 1회
- 최대 병렬 작업자 2명. 같은 파일·문맥의 작은 작업은 계획 단계에서 하나의 태스크로 합친다.
- 구현과 일반 검증은 `gpt-5.6-sol`이 기본이다.
- `gpt-5.6-terra`는 보안·인증·데이터 마이그레이션·공개 API·여러 모듈 설계 또는 Sol 1회 실패 시에만 사용한다.
- 작업자는 태스크별 최소 검증만 실행한다. 전체 검증과 독립 Codex 검증은 통합 완료 후 각각 1회만 실행한다.
- 사용자에게 더 높은 보증 수준이나 더 빠른 병렬 처리를 명시적으로 요청받은 경우에만 이 기본값을 높인다.

## 시작 조건

- 모델을 임의로 대체하지 않는다. Fable 또는 지정된 Codex 모델을 사용할 수 없으면 실제 상태와 가능한 선택지를 보고하고 멈춘다.
- 사용자 목표, 제외 범위, 대상 저장소, 완료 조건을 먼저 고정한다. 범위를 바꾸는 추정은 하지 않는다.
- 기준 커밋, 브랜치, 기존 변경, 적용 지침, 도구 버전, 검증 명령을 기록한다. 비밀 값은 기록하지 않고 환경 변수 이름과 설정 유무만 공유한다.
- 기존 변경이 있으면 전용 worktree를 우선 사용한다. 그렇지 못하고 작업 파일과 겹치면 사용자 확인 전에는 수정·스테이징·커밋하지 않는다.
- 외부 정보성 사실이 필요하면 공식 문서만 사용한다. 시장 평가가 필요한 경우에만 사람들의 의견을 별도 의견 근거로 사용할 수 있다.

상세 산출물 형식과 실행 프롬프트는 [워크플로 계약](references/workflow-contract.md)을 따른다.

## `codex-handoff` 연동

시작할 때 다음 순서로 `codex-handoff/SKILL.md`를 찾는다.

1. 이 스킬의 형제 경로 `../codex-handoff/SKILL.md`
2. 대상 저장소의 `skills/codex-handoff/SKILL.md`
3. 사용자가 지정한 경로

존재하면 `plan-format.md`의 계획 위치와 `대상`·`검증` 의미, `executor-protocol.md`의 범위·센티널만 재사용한다. Bash 실행 예시, 승인 우회, 태스크별 커밋, 재시도 규칙은 가져오지 않는다. 이 스킬의 토큰 예산·병렬화·검증·최종 커밋 규칙이 우선한다. `대상=write_set`, `검증=verify`로 해석한다. 없으면 [워크플로 계약](references/workflow-contract.md)의 자체 형식을 사용한다.

## 실행 순서

### 1. 환경 캡슐 생성

- 절대 저장소 경로, 기준 커밋, 기존 변경, 적용 지침, 검증 명령을 한 번 확인해 환경 캡슐로 기록하고 `environment_id`를 붙인다.
- 각 모델에는 캡슐 전문을 반복하지 않고 `environment_id`, 경로, 기준 커밋과 자기 태스크에 필요한 제약만 전달한다.
- `CLAUDE.md`와 `AGENTS.md` 등 도구별 지침을 모두 확인해 공통 작업 브리프에 명시한다. 서로 모순되어 결과에 영향을 주면 임의로 우선순위를 만들지 말고 차단한다.
- 동일 checkout을 쓸 때는 쓰기 범위가 겹치지 않는 태스크만 병렬 실행한다. 겹칠 가능성이 있으면 같은 기준 커밋의 독립 worktree를 사용한다.
- 의존성 설치와 생성물 갱신은 한 담당자만 수행한다. lockfile, 마이그레이션, 공용 설정처럼 여러 태스크가 만지는 파일은 별도 순차 태스크로 분리한다.
- 정렬 결과가 다르면 계획 수립 전에 해결한다. 기준 커밋이나 필수 도구가 다른 상태로 실행하지 않는다.

### 2. Fable 간결 계획

- Claude CLI를 대상 저장소에서 읽기 전용 계획 모드로 실행한다: `claude -p --model fable --permission-mode plan`.
- 먼저 로컬 검색으로 관련 파일·심볼·테스트 명령만 모아 계획 패킷을 만든다. Fable에는 전체 저장소 탐색이나 장문 설명을 요구하지 않는다.
- 계획은 태스크 표와 미확인 사항만 반환하게 한다. 각 태스크에는 의존성, 쓰기 범위, 공유 자원, 위험도, 검증 단계, 모델, 병렬 웨이브를 포함한다.
- `scripts/validate_plan.py <계획파일>`로 구조와 충돌을 검사한다. 형식 오류 때문에 Fable을 다시 호출하지 말고 로컬에서 고친다.

### 3. 계획 검토와 스케줄링

- 계획이 사용자 목표와 환경 스냅샷을 보존하는지 확인한다.
- 같은 웨이브에는 의존 관계, `write_set`, `resource_set` 충돌이 없는 태스크만 둔다. 공용 파일과 통합 작업은 뒤의 순차 웨이브로 이동한다.
- 같은 파일과 문맥을 읽는 작은 작업은 하나의 계획 태스크로 합친다. 병렬화가 총 토큰을 줄이지 못하면 순차 실행한다.
- 기본 동시 실행 수는 2다. 사용자 지정 모델이 있으면 그것을 우선한다.

### 4. Codex 병렬 구현과 작업자 검증

- 네이티브 다중 에이전트에는 전체 대화 이력을 전달하지 말고 [작업자 패킷](references/workflow-contract.md#codex-작업자-패킷)만 제공한다. CLI에서는 `codex exec -m <모델> -C <작업경로>`를 사용한다.
- 작업자마다 하나의 계획 태스크만 준다. 계획 변경, 범위 밖 수정, 커밋을 금지한다.
- 작업자는 수정 후 V0 범위 검사와 V1 태스크 검증만 실행하고 고정된 짧은 형식으로 결과를 보고한다. 전체 로그는 프롬프트에 복사하지 않고 파일 경로만 남긴다.
- 공유 checkout에서는 전체 테스트를 동시에 돌리지 않는다. V2 영향 검증은 공용 인터페이스가 바뀐 웨이브에서만 오케스트레이터가 한 번 실행한다.
- 전용 worktree 결과는 작업자가 커밋하지 않는다. 오케스트레이터가 허용된 diff만 통합 checkout에 적용하며, patch 충돌이나 범위 중첩이 생기면 자동 해결하지 않고 차단 절차로 보낸다.

### 5. 차단과 Fable 재계획

- 요구사항 모순, 계획 누락, 범위 충돌, 환경 불일치, 권한·의존성 부재, 검증 불가능을 발견하면 추정으로 우회하지 않는다.
- 작업자는 [차단 보고서](references/workflow-contract.md#차단-보고서)를 남기고 호환 센티널 `TASK_FAIL T<N>: BLOCKED <요약>`으로 종료한다. 독립적인 다른 태스크는 계속할 수 있다.
- 구현 오류는 Codex에 한 번만 재지시한다. 계획·범위·충돌 문제만 Fable에 보낸다. 권한·인증·비밀·목표 변경은 모델 호출 없이 사용자에게 요청한다.
- Fable에는 전체 계획·diff·로그 대신 차단 태스크, 관련 diff, 오류 핵심 줄, `environment_id`만 제공하고 `plan_delta`만 요청한다.
- 수정 계획이 사용자 목표·공개 인터페이스·의존성·데이터·보안 경계를 넓히면 사용자 승인을 받는다. 그 외에는 영향받은 미완료 태스크만 다시 스케줄한다.
- 같은 원인의 차단이 수정 계획 뒤에도 다시 발생하면 자동 재계획을 중단하고 사용자에게 판단을 요청한다.

### 6. 통합 및 단계별 검증

- V0 범위 검사는 태스크마다 로컬 명령으로 수행한다. 모델 검토를 쓰지 않는다.
- V1 태스크 검증은 구현 작업자가 한 번 수행한다.
- V2 영향 검증은 공용 인터페이스·공유 자원 변경 때만 웨이브 통합 후 실행한다.
- V3 전체 검증과 독립 Codex 검증은 모든 변경 통합 후 커밋 직전에 각각 한 번만 수행한다. 독립 검증은 Sol이 기본이다.
- V4 Terra 검증은 보안·인증·데이터 마이그레이션·파괴 가능 변경 또는 Sol 검증 실패 때만 추가한다.
- 독립 검증에는 최종 diff, 목표, 완료 조건만 제공한다. 구현 대화와 전체 로그는 전달하지 않는다.

### 7. 최종 게이트와 커밋

다음이 모두 참일 때만 커밋한다.

- 모든 계획 태스크가 검증 증거와 함께 완료됐다.
- 미해결 차단과 범위 밖 변경이 없다.
- 필요한 V1/V2와 최종 V3 검증이 통과했고, 고위험이면 V4도 통과했다.
- 최종 diff가 사용자 목표와 일치하고 비밀·임시 로그·불필요한 생성물을 포함하지 않는다.
- 기존 사용자 변경이 스테이징 대상에 섞이지 않았다.

`git add -A`나 포괄 glob을 쓰지 말고 확인된 파일만 명시적으로 스테이징한다. 독립 검증이 확인한 diff와 staged diff가 같은지 확인한 뒤 로컬 커밋한다. 사용자가 별도로 요청하지 않으면 push, PR 생성, 배포는 하지 않는다.

## 종료 보고

계획 파일, 모델별 담당, 완료·차단 태스크, 검증 결과, 변경 파일, 커밋 해시만 고정된 짧은 형식으로 보고한다. 성공 로그와 모델의 장문 설명은 반복하지 않는다. 커밋하지 못했다면 실패한 게이트와 보존된 작업 상태만 적는다.
