# 공개 기술 블로그: 간결·위트·실습형

목표는 "독자가 따라 하면 끝나는 글"이다. 다 읽은 독자에게 "나도 해 봐야지"가 남아야 한다. 이론을 설명하는 글이 아니라 손을 움직이게 하는 글이다.

Codex와 Claude Code 모두에서 같은 절차로 쓴다.

## 작업 순서

1. **소재와 목표 정하기**: 원본 자료(조사 문서, 코드, 사내 초안)를 읽는다. "독자가 끝에 손에 쥘 것"을 한 문장으로 정한다. 한 문장으로 안 나오면 글을 둘로 나눈다.
2. **공개 정리**: 회사와 내부 정보를 걷어 낸다(아래 "공개 정리" 절). 공개 글은 회수가 안 된다. 검색과 캐시에 남기 때문에 이 단계를 가장 먼저 한다.
3. **이론 덜기**: 문장마다 "이걸 지우면 독자가 실습 중에 막히나?"를 묻는다. 안 막히면 지운다. 원리는 한 줄 요약과 링크로 바꾼다.
4. **뼈대에 맞춰 쓰기**: 아래 "뼈대"를 따른다. 단계 이름은 내용에 맞게 바꾼다.
5. **코드 검증**: 본문의 코드 블록은 독자가 복사해 바로 돌린다. 그러므로 lint·실행·모의 실행으로 확인한다(아래 "코드 블록" 절).
6. **제목 3안·태그 3안**: 아래 절을 따른다. front matter에는 추천안(C)을 넣는다.
7. **최종 점검**: `scripts/check_post.py`를 돌린다. 실패 항목을 고친 뒤 보고한다.

## 공개 정리

- 지울 것: 회사·고객·제품 내부 이름, 내부 저장소 이름, 내부 호스트·IP·경로, 계정, 사내 규정·심사 이름, 내부 조사 결과(취약점, 장애, 수치)
- 바꿀 것: 일반 예시로 바꾼다(`my-service`, `src/api/`, `example.com`).
- 회사 이름 같은 금지어 목록은 스킬 폴더 밖의 로컬 파일에 둔다(예: `~/.config/public-tech-blog/deny.txt`). 이 스킬 저장소가 공개될 수 있어서다.

## 뼈대

```markdown
---
title: "<제목 C안>"
date: YYYY-MM-DD
tags: [<태그 C안>]
summary: "<한 문장: 무엇을 만들고 무엇을 얻는가>"
---

# <제목>

<도입 2~3문장: 공감 가는 문제 + 오늘의 해결. 위트는 여기서 한 번>

## 오늘 만들 것        <완성 모습: 작은 그림이나 3줄>
## 30초 소개          <알아야 할 것 3개 이하. 원리는 링크로>
## 준비물             <표: 항목 | 비고>
## 1단계: ...         <할 일 → 코드 → "꼭 볼 곳" 3~5개>
## 2단계: ...
## 결과 확인          <확인할 것 3개 이하>
## 사고 안 나게        <[!] 경고 3~5줄>
## 마치며             <1~2문장, 웃고 끝>
## 참고               <링크 3~5개>
```

필요 없는 절은 뺀다. 순서는 독자가 손을 움직이는 순서를 따른다.

## 문체

- 합니다체를 쓴다. 한 문장에 한 생각만 담는다.
- **위트는 양념이다.** 의인화, 비유, 가벼운 과장을 도입과 마무리에 집중하고, 절마다 많아야 한 번 쓴다. 명령어, 경고, 수치를 담은 문장에는 농담을 섞지 않는다. 웃기려다 단계가 흐려지면 실습 글은 실패한다.
- 쓰지 않는 것: 한자, 이모지(경고는 `[!]`), 특정인·집단 조롱, 밈 남발, "~인 것이다"로 끝나는 논문체.
- 전문 용어는 처음 나올 때 괄호로 한 줄 풀이한다. 독자를 비전문가로 가정한다.
- 수치와 인용에는 출처 링크를 단다. 확인하지 못한 수치는 지운다.
- 길이는 코드를 뺀 본문 60~120줄을 목표로 한다. 넘으면 이론부터 덜어 낸다.

톤을 맞출 때는 [변환 예시](references/examples.md)를 읽는다.

## 코드 블록

- 복사해서 그대로 돌아가야 한다. 자리 표시 값은 `<이름>` 꼴로 눈에 띄게 둔다.
- 작성 후 확인: 셸은 `shellcheck`, GitHub Actions는 `actionlint`, YAML은 `yamllint`, Python은 `python -m py_compile`, JS는 `node --check`를 쓴다. 외부 서비스가 필요하면 가짜 명령으로 모의 실행한다.
- 본문에서 코드 블록을 다시 뽑아 테스트한 원본과 비교한다. 편집 중에 생긴 오타를 잡기 위해서다.
- 확인하지 못한 것은 글에 숨기지 말고 작업 보고에 적는다.

## 제목 3안

| 안 | 방향 | 형식 | 적합 |
|---|---|---|---|
| A. 위트형 | 비유·의인화 | "AI 감사관을 월요일 새벽에 출근시키기" | SNS 공유, 사내 블로그 |
| B. 검색형 | 도구 이름 + 동사 + 결과 | "<도구>로 <결과> 자동화하기" | 검색 유입 |
| C. 혼합형 (기본 추천) | 위트 구절 + 도구 이름 | "<위트 구절>: <도구> 실습" | 둘 다 노릴 때 |

각 안에 장점, 단점, 적합 조건을 붙여 보고한다. 도구 이름은 원문 표기를 지킨다.

## 태그 3안

| 안 | 구성 | 적합 |
|---|---|---|
| A. 영문 | 도구 이름 kebab-case(`claude-code`, `github-actions`) + 분야(`security`) | velog, dev.to |
| B. 한글 | 붙여 쓰기(`보안점검`, `깃허브액션`, `자동화`) | 티스토리, 네이버 블로그 |
| C. 혼합 (기본 추천) | 도구 이름은 영문, 분야·행위는 한글. 5~7개 | 플랫폼을 가리지 않을 때 |

C안에는 태그 수 제한이 있을 때 먼저 뺄 태그를 적는다.

## 최종 점검

```bash
python <skill-dir>/scripts/check_post.py <글.md> [--deny-file ~/.config/public-tech-blog/deny.txt] [--deny <단어>]
```

이 스크립트는 한자, 이모지, IPv4, 금지어, 코드 블록 짝, front matter의 `title`·`tags`·`summary`를 검사한다. 하나라도 걸리면 종료 코드 1을 낸다. 본문 길이가 목표를 넘으면 경고만 낸다.
