# 변환 예시

이 파일의 예시는 톤을 맞추는 데 쓴다. 문장을 그대로 베끼지 말고 방향만 가져간다.

## 도입: 논문 서론을 공감되는 문제로

- 전: "본 글에서는 정적 분석 자동화 파이프라인의 구성 방안과 설계 원칙을 고찰한다."
- 후: "보안 점검은 늘 '다음 분기에'로 밀립니다. 그래서 대신 출근할 감사관을 하나 뽑았습니다. 연봉은 API 비용, 근무 시간은 월요일 새벽 3시 17분입니다."

문제를 먼저 말하고 해결은 한 문장으로 끝낸다. 위트는 도입에서 한 번이면 충분하다.

## 개념: 원리 설명을 한 줄 비유로

- 전: "탐색 에이전트와 검증 에이전트를 분리하는 이유는 자기 검증 시 확증 편향으로 오탐이 늘기 때문이다."
- 후: "찾는 쪽과 검증하는 쪽이 다릅니다. 자기 답안을 자기가 채점하면 늘 만점이라서요."

## 설정: 규칙 나열을 효과 중심으로

- 전: "GITHUB_TOKEN 권한은 permissions 키로 워크플로 또는 잡 단위로 지정할 수 있으며, 최소 권한 원칙에 따라 각 잡에 필요한 범위만 부여한다."
- 후: "audit 잡은 읽기만, publish 잡은 이슈 쓰기만 합니다. 코드 주석에 숨은 문장이 감사관을 꼬드겨도 쓸 권한이 없습니다."

독자가 궁금한 것은 키 이름보다 "그래서 무엇이 막히는가"다.

## 경고: 농담을 빼고 담백하게

- 전(나쁜 위트): "API 키를 아무 데나 두면 지갑이 울어요"
- 후: "[!] API 키와 이슈 쓰기 권한을 한 잡에 모으지 마세요."

경고에 농담이 섞이면 독자가 가볍게 넘긴다.

## 이론 덜기: 표 세 개를 세 줄로

- 전: 설계 원칙 5개, 선택지 비교표 3개, 측정 지표 표 1개
- 후: "30초 소개" 불릿 3개와 원문 링크 1개

판단 기준은 하나다. 지워도 독자가 실습 중에 막히지 않으면 지운다.

## 공개 정리: 내부 이름을 일반 예시로

- 전: "사내 레포 A와 B는 자체 프레임워크 기반이며 `/srv/a/app/Auth.php`에서 로그인을 확인한다."
- 후: "인증 확인 위치: `src/middleware/auth.ts`"

## 마무리: 요약 대신 한 방

- 전: "이상으로 자동화 구성 방법과 주의 사항을 살펴보았다."
- 후: "이제 보안 점검을 다음 분기로 미룰 핑계가 하나 줄었습니다. 월요일 아침 이슈 목록을 열어 볼 용기는 각자 챙기셔야 합니다."
