# ESCALATION — 언제 멈추고 사용자에게 묻는가

> LOAD WHEN: 상시. 판단이 갈리거나 정보가 없을 때마다 이 문서의 분류를 적용한다.
>
> 이 키트의 핵심 설계 목표: **에이전트는 사용자 결정/수작업이 필요한 지점까지 스스로 굴러간다.**
> 그 지점에 닿으면 **추측으로 밀고 나가지 않고**, 구체적 선택지를 만들어 묻는다.

---

## 1. 3단 분류

에이전트는 마주친 불확실성을 아래 셋 중 하나로 분류한다.

| 분류 | 정의 | 행동 |
|---|---|---|
| **AUTO** | 문서/스펙/코드에서 답을 유도할 수 있음. 되돌리기 쉬움. | 그냥 한다. 보고서에 한 줄 남긴다. |
| **ASSUME** | 답이 없지만 합리적 기본값이 명확. 되돌리기 쉬움. | 가정을 **명시**하고 진행. 보고서 `가정` 항목에 기록. 나중에 뒤집혀도 손실 작음. |
| **STOP** | 아래 STOP 목록에 해당. 틀리면 이후 작업 전체가 무의미해지거나 되돌리기 비쌈. | **즉시 중단.** 질문 발행. 상태 파일에 `BLOCKED` 기록. |

**의심스러우면 ASSUME 이 아니라 STOP 쪽으로 기울인다** — 단, STOP 은 진짜로 막힐 때만. 사소한 것마다 묻지 않는다.

## 2. STOP 조건 목록

### 2.1 사람만 할 수 있는 일 (MANUAL — 공통)

| 상황 | 왜 |
|---|---|
| Unity 계정 로그인 / 라이선스 활성화 | 자격증명 입력은 에이전트가 하지 않는다 |
| Unity Editor GUI 를 실제로 띄워야 하는 작업 | 헤드리스로 대체 불가한 경우 |
| 유료 에셋 구매 / 스토어 결제 | 결제 행위 금지 |
| 외부 에셋 팩 다운로드 승인 | 다운로드는 사용자 승인 필요 |
| 컨셉아트 원본 이미지 제공 | 에이전트는 이미지를 창작하지 못한다 |
| 관리자 권한이 필요한 설치 (심볼릭 링크, 시스템 PATH) | 권한 상승 필요 |
| Git 커밋/푸시 | 사용자가 명시적으로 요청하지 않는 한 안 함 |

### 2.2 V 트랙에서 사용자만 결정할 수 있는 일 (DECISION)

| 상황 | 왜 |
|---|---|
| **아트 디렉션 확정** — VISUAL_SPEC 의 팔레트/셰이프 랭귀지/카메라 최종값 | 취향·기획 영역. 틀리면 이후 전부 재작업 |
| **프로젝트 모드** — GREENFIELD 인가 VISUAL REBASE 인가 | 파이프라인 경로 자체가 달라짐 |
| **프로파일** — 3D 인가 2D 인가, 혼합인가 | 스펙 스키마가 달라짐 |
| **에셋 조달 전략** — 기존 재활용 / 무료 팩 / ProBuilder / 신규 필요 | 예산·저작권·품질 트레이드오프 |
| **어떤 무료 에셋 계열을 쓸 것인가** | 계열을 섞으면 통일성이 깨짐. 되돌리기 비쌈 |
| **UNDEFINED 항목 처리** — 컨셉아트에 없는 영역(야간, 실내, 인벤토리 등) | 상상으로 채우면 스타일 붕괴 |
| **Asset Replacement Matrix 의 DELETE 판정** | 데이터 손실 |
| **기존 Scene/Prefab 구조 리팩터링 범위** | 게임플레이 회귀 위험 |
| **Golden Scene 합격 판정** | 최종 미적 판단은 사람의 몫 |

### 2.2b 코드 트랙에서 사용자만 결정할 수 있는 일 (DECISION)

| 상황 | 스테이지 | 왜 |
|---|---|---|
| **Acceptance Criteria 를 검증 가능한 형태로 못 만듦** | C1 | 스펙 확정은 사용자 몫 |
| **모르는 수치값** (쿨다운, 데미지, 속도 등)을 코드/테스트에서 유도 불가 | C1 | 게임 밸런스는 기획 영역 |
| **기존 시스템 확장 vs 신규 생성** | C2 | 아키텍처 방향. 되돌리기 비쌈 |
| **테스트가 없어 회귀 검증 불가** — 테스트 선작성 여부 | C2/C3 | 작업 범위가 크게 달라짐 |
| **고위험 변경 승인** (SerializeField / Prefab / Scene / SO / asmdef) | C3 | 직렬화 데이터 손실 위험 |
| **매우 높음 변경 승인** (Input / Addressables / Build Settings) | C3 | 빌드해야 드러나는 사고 |
| **태스크 분할 범위** — STEP 이 과도하게 많을 때 | C4 | 작업 단위는 사용자 판단 |
| **테스트를 고쳐야만 통과 가능해 보임** | C5 | **절대 임의로 고치지 않는다.** 스펙 변경인지 확인 |
| **계약 범위 밖 변경을 되돌릴지 유지할지** | C6 | 의도치 않은 변경 처리 |
| **기본 브랜치 직접 커밋 여부** | C6 | 브랜치 전략 |

### 2.3 스펙 충돌 / 정보 부재 (CONFLICT — 비주얼 트랙)

| 상황 | 왜 |
|---|---|
| VISUAL_SPEC 과 컨셉아트가 서로 모순 | 어느 쪽이 진실인지 사람이 정해야 함 |
| 컨셉아트에서 측정값을 신뢰 수준 이상으로 추정해야 함 | 에이전트의 눈은 정확한 계측기가 아님 |
| 요청받은 시각 결과가 현재 에셋으로 물리적으로 불가능 | 범위 조정 필요 |
| 스테이지 EXIT GATE 를 3회 루프 이상 통과 못 함 | 접근 자체가 틀렸을 가능성 |

### 2.4 위험 작업 (RISK — `references/policy/SAFETY_RULES.md` 와 연동)

| 상황 |
|---|
| 기존 Editor 삭제 / `--replace` / `--remove-old` |
| `ProjectVersion.txt` 변경 (major.minor 마이그레이션) |
| 기존 MCP 설정 삭제 |
| Git working tree 파괴 (`reset --hard`, `clean -fd`) |
| 사용자 파일 삭제 |
| `Packages/manifest.json` 직접 편집 |

## 3. 질문 발행 형식 (필수 템플릿)

STOP 에 걸리면 **아래 형식 그대로** 출력한다. 막연한 질문 금지.

```markdown
## ⏸ BLOCKED — 사용자 결정 필요

**스테이지:** S{n} {STAGE_NAME}
**분류:** MANUAL / DECISION / CONFLICT / RISK
**여기까지 완료:** {한 줄}
**막힌 이유:** {한 줄 — 왜 에이전트가 결정할 수 없는지}

### 결정 항목: {한 문장 질문}

| # | 선택지 | 결과 | 되돌리기 | 비용/리스크 |
|---|---|---|---|---|
| 1 | ... | ... | 쉬움/보통/어려움 | ... |
| 2 | ... | ... | ... | ... |
| 3 | ... | ... | ... | ... |

**에이전트 추천:** {번호} — {이유 한 줄}

### 결정을 기다리는 동안 할 수 있는 일
- {이 결정과 무관하게 진행 가능한 작업. 없으면 "없음"}

### 결정 후 자동 재개될 작업
- {선택지별로 무엇이 실행되는지}
```

### 규칙
- 선택지는 **2~4개**. 자유서술 요구 금지 (사용자가 "기타"를 쓸 수는 있다).
- 각 선택지는 **구체적 수치/경로/이름**을 포함해야 한다. "적절히 조정" 같은 표현 금지.
- **에이전트 추천을 반드시 넣는다.** 사용자가 "그냥 추천대로" 라고 답할 수 있어야 한다.
- 결정과 **무관하게 진행 가능한 작업은 먼저 다 끝내놓고** 묻는다. 놀면서 묻지 않는다.

## 4. MANUAL 항목 안내 형식

사람이 손으로 해야 하는 일은 **복붙 가능한 명령/절차**로 준다.

```markdown
## 🖐 사용자 수작업 필요

**무엇:** {한 줄}
**왜 에이전트가 못 하는가:** {한 줄}

### 절차
1. ...
2. ...

```bash
{복붙 가능한 명령}
```

### 완료 확인 방법
{사용자가 무엇을 보면 성공인지}

### 끝나면
"완료" 라고 알려주면 {다음 작업}부터 자동 재개한다.
```

## 5. 묻지 말아야 할 것 (안티패턴)

에이전트가 흔히 과잉 질문하는 항목 — 이것들은 **그냥 하라.**

| 묻지 마라 | 대신 |
|---|---|
| "파일 이름을 뭘로 할까요?" | 키트에 지정된 이름 사용 |
| "이 폴더를 만들어도 될까요?" | 만든다 |
| "린터를 돌려도 될까요?" | 돌린다 |
| "스크린샷을 찍어도 될까요?" | 찍는다 |
| "다음 스테이지로 갈까요?" | 게이트 통과했으면 간다 |
| "코드 스타일을 어떻게 할까요?" | 주변 코드에 맞춘다 |
| "계획이 괜찮은가요?" | 실행하고 결과를 보여준다 |
| "정말 진행할까요?" | 안전 규칙 위반이 아니면 진행한다 |
| "테스트를 돌려도 될까요?" | 돌린다 |
| "커밋해도 될까요?" (스테이지 완료 시) | 커밋하고 push 한다 |
| "이 상수를 어디에 둘까요?" | `CODE_ARCHITECTURE.md` 규칙대로 둔다 |
| "변수명을 뭘로 할까요?" | 주변 코드 관례를 따른다 |

**반대로, 아래는 반드시 물어라** — 이걸 추측하면 이후 전부 재작업이 된다.

**V 트랙**
- 아트 디렉션 최종값 (VISUAL_SPEC 확정)
- 3D/2D 프로파일
- GREENFIELD / REBASE 모드
- 에셋 조달 전략 / 무료 팩 계열
- DELETE 판정
- Golden Scene 합격 여부
- UNDEFINED 영역 처리 방침

**C 트랙**
- 검증 불가능한 Acceptance Criteria
- 코드에서 유도할 수 없는 수치값 (밸런스)
- 기존 시스템 확장 vs 신규 생성
- 고위험 변경 승인 (SerializeField / Prefab / Scene / SO / asmdef)
- 매우 높음 변경 승인 (Input / Addressables / Build Settings)
- 테스트를 고쳐야 통과 가능해 보일 때
- 계약 범위 밖 변경의 처리

## 6. 재개 프로토콜

사용자가 결정을 답하면:

1. 답을 해당 스펙 파일에 **영구 기록**한다 (`VISUAL_SPEC.yaml`, `PIPELINE_STATE.md` 의 `decisions:`).
2. `PIPELINE_STATE.md` 의 상태를 `BLOCKED` → `IN_PROGRESS` 로 바꾼다.
3. **같은 질문을 다시 하지 않는다.** 기록된 결정은 이후 세션에서도 유효하다.
4. 결정이 뒤집히면 영향받는 스테이지를 상태 파일에 `INVALIDATED` 로 표시하고 어디부터 재작업인지 보고한다.
